# Upgrading 2.0.x to 2.1.0

2.1.0 changes how the schema is migrated and how stored secrets are sealed.
Both are one-way. Take a database backup first (CNPG `Backup` to the
off-host ObjectStore, or `pg_dump -Fc`) and keep `helm get values`.

## 1. Baseline the migration bookkeeping (once)

2.0.x tracked migrations in golang-migrate's `schema_migrations` (version 81).
2.1.0 applies its embedded goose migrations at server boot and reads
`public.goose_db_version`. On a 2.0.x database that table does not exist, so
goose would start at 00001 on a populated schema and fail. Record versions
1–81 as applied **before** the first 2.1.0 pod starts:

```sql
\set ON_ERROR_STOP on
BEGIN;
DO $$
BEGIN
  IF to_regclass('public.goose_db_version') IS NOT NULL THEN
    RAISE EXCEPTION 'goose_db_version already exists; baseline already done';
  END IF;
  IF (SELECT count(*) FROM public.schema_migrations) <> 1
     OR (SELECT max(version) FROM public.schema_migrations) <> 81
     OR (SELECT bool_or(dirty) FROM public.schema_migrations) THEN
    RAISE EXCEPTION 'schema_migrations is not clean at version 81';
  END IF;
END $$;
CREATE TABLE public.goose_db_version (
  id integer PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
  version_id bigint NOT NULL,
  is_applied boolean NOT NULL,
  tstamp timestamp NOT NULL DEFAULT now()
);
INSERT INTO public.goose_db_version (version_id, is_applied) VALUES (0, true);
INSERT INTO public.goose_db_version (version_id, is_applied)
  SELECT v, true FROM generate_series(1, 81) AS v ORDER BY v;
COMMIT;
```

Run it as the database owner (CNPG: `kubectl exec <primary> -c postgres --
psql -U postgres -d astronomer`, then `ALTER TABLE public.goose_db_version
OWNER TO astronomer;`). The DDL is exactly what goose v3.29 creates.
`schema_migrations` stays behind, inert. Rehearse on a restored copy:
`server migrate -database <copy-dsn>` must print
`schema at version 84 (3 applied)`.

## 2. Replace the Fernet key with an age keyring

`astro admin generate-encryption-key --label <id>` prints
`<id>:AGE-SECRET-KEY-1…`. Put it in `secrets.encryptionKey` (or the
`ASTRONOMER_ENCRYPTION_KEY` key of `secrets.existingSecret`). Fernet keys are
rejected at render and at startup. Store the key off-cluster.

Migration 00082 discards every sealed value written under Fernet. After the
upgrade, re-enter: Helm repository / registry / git credentials, cloud
credentials, SSO client secrets, Dex connectors, SMTP/SIEM/vault/webhook
secrets. SSO sessions and TOTP enrolments are deleted (users sign in and
re-enrol). A Charlie connection loses its local trust material and must be
re-onboarded. Agent and registration tokens are hashed, not sealed, and keep
working.

## 3. Values

Remove `image.migrate`, `image.allowSchemaSkew` and `migrate.*`; drop a pinned
`preflight.databaseSchema.targetVersion: 81` (the chart's value is 84). Point
the DR images at 2.1.0 (PostgreSQL 17 client) and the restore-drill sidecar at
`postgres:17-alpine`. Objects created by hand for the 2.0.1 chart gaps (CNPG
kube-apiserver / object-store egress, DR job DB ingress, the Barman
`ObjectStore`, the delivery trust Secret) are now chart-rendered: adopt them
into the release (label `app.kubernetes.io/managed-by=Helm`, annotate
`meta.helm.sh/release-name/-namespace`) or delete them after the upgrade.

## 4. After the upgrade

- `/readyz` is green and the server log shows
  `database migration applied` for 82–84.
- Promote the new system release: `astro delivery system-rollout start` then
  `approve` (it stays `draft` until you do).
- Image admission: release candidates are signed by
  `release.yaml@refs/tags/vX.Y.Z-rc.N`; the shipped `ClusterImagePolicy`
  admits that subject.
