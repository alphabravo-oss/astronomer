# Helm4 consumer migration

Status: source draft,2026-10-10. Runtime, module-closure and install/rollback qualification are pending. This document authorizes no deployment or publication and does not mark the standalone CLI or embedded SDK qualified.

The version authority discovered upstream standalone Helm4.3.0 and retained the application's qualified Helm3.21.4 SDK graph under the W11 exception. The source draft changes the direct application module to `helm.sh/helm/v4 v4.3.0`; `go.sum`, transitive closure and authority selection are deliberately still unchanged until the isolated compiler window. A source-only module declaration is not an adopted or tested build. Flux keeps its upstream controller distribution and tested dependency graph; application MVS must not force a downstream controller fork.

Each consumer has a separate behavior and qualification boundary:

| Consumer | Source migration | Required evidence before adoption |
| --- | --- | --- |
| Agent operation handler | chart-v2 loading; request-local Kubernetes getter; release-v1 conversion; explicit legacy waits and client-side updates | actual joined install/upgrade/uninstall/rollback; history/marker/status/error parity; values and hooks; canceled transport/storage/discovery/waits |
| Agent process configuration | capture Helm4 settings at the existing composition boundary; overwrite new content-cache/color fields | injected settings override ambient values; writable non-root paths; declared repository policy |
| Charlie installer | same owned Kubernetes and registry transports; preserve no-workload-wait hook behavior and release identity | apply/install/upgrade/uninstall; credentials remain private; cancellation joins; interrupted history and activation semantics |
| Catalog OCI ingestion | standalone registry imports migrate without delivery-policy replacement | existing authentication, enumeration/archive limits and signature/digest outcomes |
| Canonical delivery OCI resolver | registry imports only | complete existing owned destination/trust/immutable-reference suite; no transport or credential policy duplication |
| Canonical delivery HTTP resolver | repo-v1 index imports only | existing exact-version/index/digest/signature/trust and bounded-transfer suite |
| Catalog hydration | chart-v2 loader imports only | exact archive/schema/values/metadata results and existing HTTP policy |
| Worker repository synchronization | repo-v1/index and chart-v2 loader imports only | authentication, bounded index/archive, ingestion and resource extraction parity |
| Distribution renderer | chart-v2 loader/util and existing engine/action imports | deterministic chart rendering, Kubernetes capabilities, value precedence and signed output contracts |
| Standalone scripts/CI | preserve existing pins until each consumer is characterized | exact verified Helm4 executable/version; rendering and CLI strategy behavior; no ambient Helm3 qualification |
| Flux helm-controller | preserve upstream release and dependency graph | actual coexistence with supported Flux; no application SDK dependency override |

The committed import baseline binds14 Go files/31 import occurrences; the CLI/controller baseline records39 tracked files/146 lexical locations under scripts/deploy/.github. These source locations include fixture and policy text; they do not prove execution or that every literal is a production tool consumer. The historical plan's approximate28 count is not rewritten.

Helm4's install and upgrade cancellation paths start a worker and can select the canceled context before that worker finishes. Passing the owned context directly therefore cannot prove mutation has stopped. The source adapter invokes the SDK with a control context that retains values but suppresses early-return cancellation. Storage, discovery, REST mapping, raw client configuration, every HTTP request/body and wait path receive the separately owned operation context. SDK return remains synchronous with its worker; the owner remains alive until return, and cancellation is included in the final error. Actual SDK worker/storage/hook tests must prove this design before qualification; source inspection alone does not.

The getter copies REST configuration and chains its original transport. It builds request-local discovery/mapper clients rather than delegating to the original unbound getter. The transport preserves narrower SDK deadlines and request values, fills missing owner values, and keeps cancellation active until body EOF/Close. Whole-operation deadlines cover background callers as well as earlier caller deadlines. Legacy waits also receive `kube.Client.WaitContext`; wait options alone do not bind that strategy. Rollback and uninstall expose only synchronous `Run` in the inspected upstream API, so their internal requests and waits use the same owned getter.

Agent install/upgrade/rollback preserve workload readiness through explicit `LegacyStrategy`; Charlie and uninstall preserve existing hook-only behavior. Install server-side apply is disabled and upgrade/rollback use explicit `"false"`, preserving client-side update ownership. The typed CLI adapter separately uses Helm4 `--wait=legacy`, `--server-side=false` and `--rollback-on-failure`; historical Helm3 argv remains separate. No bare Helm4 `--wait` or deprecated `--atomic` implicitly selects new watcher/ownership behavior. The application keeps chart-v2/release-v1 storage and rejects an unsupported representation instead of translating it silently. Existing pending-rollback marker is written at the first durable revision creation; public protocol fields remain unchanged.

The remaining HTTP chart-download slice is a real blocker. Helm's standard HTTP getter creates background requests and accepts a concrete `*http.Transport` rather than an injectable context-bound client. The current agent payload has no HTTP credential/CA or origin policy fields; existing operator repository files may contain named-repository credentials/CA settings. A new bounded locator must reuse canonical `internal/httpclient` destination, CA and body-limit primitives plus standard Helm repository/version/cache/loader APIs. Private origins/CIDRs must come from narrow operator-owned process configuration, never from the caller's chart URL or unrelated catalog policy. Existing private/offline repository behavior needs before/new-default/configured-policy characterization. No broad `AllowPrivate`, ambient proxy grant, partial-body cancellation workaround or separate signature verifier is selected.

CNPG Cluster/PVC/ObjectStore/backup/operator identity, PostgreSQL major, Valkey selection and Flux ownership are unchanged in this source stage. Supported CNPG/K3s1.36 and experimental1.37 lanes remain distinct. Chart option matrix, hooks/CRD rollback safety, actual signed-chart install, interrupted upgrade/resume/history and compatible data-preserving rollback remain open.

The source configuration adds optional `HELM_REPOSITORY_DESTINATION_POLICY`, parsed independently of delivery signing or catalog trust. The agent captures it once at startup; the server injects it into embedded-agent and Charlie settings. It uses the existing destination-policy JSON format: for example `{"origins":[{"url":"https://charts.internal.example:8443","cidrs":["10.42.0.12/32"]}]}` authorizes that exact operator origin and actual destination CIDR. An empty policy keeps canonical public HTTPS defaults. Private repositories will require an explicit operator policy when the bounded locator is connected; previous implicit private destination access will not be described as preserved by default. Loopback and metadata endpoints remain denied, even if listed. Existing named repository credentials and CA files must still be honored by the locator; this configuration is destination authority only. Configured private transfer and old/default behavior remain unqualified until their actual fixtures run.
