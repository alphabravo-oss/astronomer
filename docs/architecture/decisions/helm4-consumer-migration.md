# Helm4 consumer migration

Status: focused SDK and private HTTP fixtures qualified,2026-10-10; complete proxy source draft and live install/rollback qualification remain pending. This document authorizes no deployment or publication and does not mark the standalone CLI or embedded SDK qualified.

The version authority discovered upstream standalone Helm4.3.0 and retained the application's qualified Helm3.21.4 SDK graph under the W11 exception. The source draft changes the direct application module to `helm.sh/helm/v4 v4.3.0`; The reviewed isolated module closure and focused compilation/tests are retained under W11 assurance evidence. Authority selection still retains the qualified prior SDK until complete consumer and live gates pass. Module closure and focused fixtures do not establish production adoption. Flux keeps its upstream controller distribution and tested dependency graph; application MVS must not force a downstream controller fork.

The committed import baseline binds14 Go files/31 import occurrences; the CLI/controller baseline records39 tracked files/146 lexical locations under scripts/deploy/.github. These source locations include fixture and policy text; they do not prove execution or that every literal is a production tool consumer. The historical plan's approximate28 count is not rewritten.

Helm4's install and upgrade cancellation paths start a worker and can select the canceled context before that worker finishes. Passing the owned context directly therefore cannot prove mutation has stopped. The source adapter invokes the SDK with a control context that retains values but suppresses early-return cancellation. Storage, discovery, REST mapping, raw client configuration, every HTTP request/body and wait path receive the separately owned operation context. SDK return remains synchronous with its worker; the owner remains alive until return, and cancellation is included in the final error. Actual held SDK install/upgrade worker, hook, storage and direct-cancellation control fixtures passed on frozen c1de5668. They qualify the focused ownership behavior, not live Kubernetes install or rollback.

The getter copies REST configuration and chains its original transport. It builds request-local discovery/mapper clients rather than delegating to the original unbound getter. The transport preserves narrower SDK deadlines and request values, fills missing owner values, and keeps cancellation active until body EOF/Close. Whole-operation deadlines cover background callers as well as earlier caller deadlines. Legacy waits also receive `kube.Client.WaitContext`; wait options alone do not bind that strategy. Rollback and uninstall expose only synchronous `Run` in the inspected upstream API, so their internal requests and waits use the same owned getter.

Agent install/upgrade/rollback preserve workload readiness through explicit `LegacyStrategy`; Charlie and uninstall preserve existing hook-only behavior. Install server-side apply is disabled and upgrade/rollback use explicit `"false"`, preserving client-side update ownership. The typed CLI adapter separately uses Helm4 `--wait=legacy`, `--server-side=false` and `--rollback-on-failure`; historical Helm3 argv remains separate. No bare Helm4 `--wait` or deprecated `--atomic` implicitly selects new watcher/ownership behavior. The application keeps chart-v2/release-v1 storage and rejects an unsupported representation instead of translating it silently. Existing pending-rollback marker is written at the first durable revision creation; public protocol fields remain unchanged.

The original HTTP chart-download ownership gap required replacing the getter. Helm's standard HTTP getter creates background requests and accepts a concrete `*http.Transport` rather than an injectable context-bound client. The current agent payload has no HTTP credential/CA or origin policy fields; existing operator repository files may contain named-repository credentials/CA settings. A new bounded locator must reuse canonical `internal/httpclient` destination, CA and body-limit primitives plus standard Helm repository/version/cache/loader APIs. Private origins/CIDRs must come from narrow operator-owned process configuration, never from the caller's chart URL or unrelated catalog policy. Existing private/offline repository behavior needs before/new-default/configured-policy characterization. No broad `AllowPrivate`, ambient proxy grant, partial-body cancellation workaround or separate signature verifier is selected.

CNPG Cluster/PVC/ObjectStore/backup/operator identity, PostgreSQL major, Valkey selection and Flux ownership are unchanged in this source stage. Supported CNPG/K3s1.36 and experimental1.37 lanes remain distinct. Chart option matrix, hooks/CRD rollback safety, actual signed-chart install, interrupted upgrade/resume/history and compatible data-preserving rollback remain open.

The source configuration adds optional `HELM_REPOSITORY_DESTINATION_POLICY`, parsed independently of delivery signing or catalog trust. The agent captures it once at startup; the server injects it into embedded-agent and Charlie settings. It uses the existing destination-policy JSON format: for example `{"origins":[{"url":"https://charts.internal.example:8443","cidrs":["10.42.0.12/32"]}]}` authorizes that exact operator origin and actual destination CIDR. An empty policy keeps canonical public HTTPS defaults. Private repositories will require an explicit operator policy when the bounded locator is connected; previous implicit private destination access will not be described as preserved by default. Loopback and metadata endpoints remain denied, even if listed. Existing named repository credentials and CA files must still be honored by the locator; this configuration is destination authority only. The configured private TLS/version/BasicAuth/CA/body-cancellation fixture and default/loopback-denial tests passed in the focused c1de5668 lane. Broader consumer and live cluster behavior remain unqualified.

The focused locator replaces the HTTP/HTTPS getter used by standard Helm repository and downloader APIs. It captures the operator repository entry separately from chart coordinates, preserves named cached-index selection and the first cached owner of a direct chart URL, and binds basic credentials, CA files and client certificates to that snapshot. Getter options generated later cannot grant credentials or widen policy. `PassCredentialsAll` is accepted only from the operator file; the canonical destination check still applies, and cross-origin redirects strip credential headers. A client-certificate request rejects a cross-origin redirect because its TLS identity is transport-scoped. No TLS verification bypass is added. Repository indexes are bounded to8MiB and chart bodies to64MiB, before allocation and for streaming bodies. Temporary index paths use injected repository cache rather than ambient Helm paths; content caching and version lookup remain upstream implementations. OCI registry and local chart loading remain distinct. External downloader plugin protocols have no qualified owned transport in this stage and are rejected; their compatibility qualification remains open.

Helm repository proxy routing is captured once at the existing server/agent process configuration boundary. Nonempty uppercase `HTTP_PROXY`, `HTTPS_PROXY` and `NO_PROXY` take precedence over their lowercase variants, retaining distinct HTTP/HTTPS endpoints and the established `httpproxy` bypass matcher. An explicit `HELM_REPOSITORY_PROXY_URL` overrides both routes; `HELM_REPOSITORY_NO_PROXY` overrides bypass selection, including an explicitly empty value. An inherited bypass with no proxy is inert. Embedded-agent and Charlie receive copied typed values; runtime consumers never read the environment. Other delivery/catalog proxy inputs and unrelated agent traffic remain unchanged.

Captured routes grant no network authority. Each repository and proxy origin must satisfy the independently configured Helm destination policy, and actual dial addresses are checked. An HTTP proxy is supported only by an exact operator origin with entirely RFC1918/ULA CIDRs; public plaintext proxies remain unsupported. Operators migrating a private HTTP proxy must add its exact origin/CIDR policy, for example an origin `http://proxy.internal:3128` and its owned private network, separately from repository authority. This is an explicit product constraint and configuration migration, not an automatic private-access grant. Server or agent startup rejects a captured plaintext proxy lacking that exact private policy, even before a Helm operation; deployments with existing standard HTTP(S)_PROXY values must configure the policy or explicitly select an allowed Helm proxy route before migration. Empty policy retains canonical public HTTPS defaults. Ambiguous simultaneous raw/typed inputs, malformed proxy paths/queries/fragments and oversized routing/bypass values fail with static diagnostics that omit userinfo. Proxy credentials are operator secrets, retained separately from credential-free origin validation and sent only by standard Go proxy/CONNECT authentication; do not place them in chart values, command output or support bundles.

`NO_PROXY` changes the selected route and cannot authorize a repository or bypass its redirect/address checks. Typed routing does not resolve an unused proxy on a bypass; selected proxy DNS and its actual dial are context-bound. Existing generic `DestinationOptions.ProxyURL` consumers retain their earlier HTTPS-only/no-userinfo constructor semantics. No ambient proxy is discovered by the canonical transport itself.

The unchanged transport's actual target-mutual-TLS versus HTTPS CONNECT proxy fixture reached a genuine failed assertion: the proxy received the repository's client certificate. The proposed single-transport first-hop TLS refinement keeps repository certificates and `GetClientCertificate` out of the HTTPS proxy handshake while retaining target client authentication inside standard CONNECT or a direct/bypass request. Both proxy and repository TLS remain verified against configured trust; no TLS verification disabling, second downloader or new broad credential API is introduced. The unchanged regression and added HTTP CONNECT/proxy-auth/named-version/CA/target-client-identity/bypass/authority/cancellation fixtures are source-only AFTER proposals, not executed acceptance evidence.

Standard CONNECT sends the original target hostname. Local repository DNS validation does not pin the proxy's independently resolved target IP, so the explicit operator proxy remains a network/DNS trust boundary. Proxy-only names, remote target address enforcement and separate proxy trust/client-auth conventions remain unqualified. Do not infer a destination-address-pinning claim across CONNECT.

Downloader-plugin compatibility is also open. The tracked-source inventory checks install/update/list/uninstall commands, custom protocol literals and process plugin-path configuration; dynamic chart coordinates and private operator plugin directories are outside that read-only inventory. Preserving the `HELM_PLUGINS` setting does not qualify plugin execution. The owned HTTP locator supports HTTP/HTTPS, standard local loading and the separately owned OCI path; an external downloader protocol has no qualified context-bound transport and is explicitly rejected. Private operator plugin deployment must be inventoried and qualified before claiming parity for that workflow.
