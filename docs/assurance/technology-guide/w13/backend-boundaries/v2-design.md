# Separate v2 backend contract proposal

This document proposes a future v2 program. It authorizes no new endpoint, storage migration, SDK layout break, component replacement or customer rollout. The W13 preference extraction is a compatible internal service refactor plus separately characterized invalid-input/idempotency corrections; v1 remains the shipped contract. Release/version policy, published compatibility dates and customer approval belong to a separate reviewed v2 milestone.

## Compatibility period and ordering

Propose at least one full supported release cycle with v1 and v2 routes/clients available together, and no earlier than two published release milestones before v1 retirement. These are minimum design targets, not committed calendar dates. Customer adoption, agent-version support and migration inventory may require a longer period. Define dates, explicit supported-version matrix, deprecation headers/documentation and version-aware telemetry at v2 approval; never infer retirement from a component upgrade.

1. Freeze v1 OpenAPI/SDK binary and wire fixtures, immutable protocol and database-reader inventory. Characterize current authorization, audit/rollback, idempotency and cancellation on both supported PostgreSQL majors and actual agent/SSO cases.
2. Expand database constraints/columns/readers only after a read-only invalid-row inventory. New migrations are reversible until contract-stage adoption, preserve the declared schema floor and cannot guess-repair, delete or disable customer records. Ship old/new reader adapters before switching writers.
3. Ship server-side internal domain interfaces and dual public adapters before customer clients use v2. Deploy explicit feature capability/version discovery. Validate new required constructor capabilities at central composition while retaining v1 optional-feature behavior.
4. Upgrade agent protocols only with negotiated compatibility and durable checkpoint/credential/generation tests. Old accepted intent continues while disconnected. Rotate credential ownership only through the established SSA/RBAC and tombstone graph, never by copying secrets into a generic service.
5. Publish new SDK/browser/CLI consumers with opt-in v2 behavior and explicit continuation/error handling. Keep released v1 type/method signatures and wire envelopes available. Avoid a global DTO alias that gives old clients changed nullability or counts.
6. Run migration/import tooling in read-only preview first, produce bounded content-free discrepancies and CAS revisions, then apply only individually approved compatible repairs. Tool retries need durable receipts; customer backup/restore and old/new application schema compatibility must be demonstrated before contract-stage rollout.
7. Remove v1 adapters or old columns only in an independently approved breaking release after actual client inventory, communications, completed migrations, recovery rehearsal and release-gate evidence. A Helm rollback does not automatically undo data migrations.

## Migration tools and customer impact

The proposed toolkit has separate read-only inventory, redacted export, dry-run mapping and transactional CAS import commands. Each output binds schema version, exact source/release identity and ownership, not private payload content. Imports validate actor/tenant scope and original row revision; task/audit claimed or delivered records are never altered in place. There is no automatic cross-tenant remap or provider-secret export. A compatibility adapter should report an unmappable old row as an owned error instead of inventing defaults.

Expected customer work is updating automation to explicit operation receipts, handling scoped 400/409 errors, adopting opaque continuation where documented, migrating intentionally changed settings shape, and upgrading agents only when the selected compatibility matrix permits. Existing cluster and project identities, namespace grants, audit provenance and offline reconciliation must survive. Document any unavoidable write downtime, backup prerequisites, schema-floor implications and API-token permission changes per release. Preference internal extraction alone requires none of those public migrations.

## Decision and evidence gates

The architectural direction is one transport-neutral domain service per cohesive state owner, narrow query/transaction capabilities, explicit actor/scope and central constructors. Legitimate cross-domain orchestrators—SSO account/group/session commit, builtin delivery/registration, durable resource mutation/audit, and upgrade recovery—remain named adapters with explicit transactions or postcommit boundaries. Moving every SQL/Kubernetes call out of handlers at once would conceal rather than resolve their different ownership rules.

Before approving implementation, select exact public changes and publish old/new examples, reader/writer compatibility, migration commands, customer period, rollback/recovery constraints and named acceptance inventory. Acceptance must include actual released SDK fixtures, source-bound dependency and JSON/SQL gates, real database rollback/concurrency, and live identity/agent/offline cases relevant to changed domains. W02 source-security, W07 wider collection correctness and W14 recovery qualification remain open program gates; this proposal cannot waive them.
