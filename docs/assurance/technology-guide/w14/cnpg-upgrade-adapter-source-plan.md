CNPG ownership and upgrade adapter implementation scope

This source successor explicitly reads the deployed release's full Helm values and uses the canonical postgresMode semantics. cloudNativePG never becomes external merely because the legacy component=postgres Pod list is empty. The legacy bootstrap now refuses that mode before issuing a database command; this is an explicit current limitation, not CNPG support or W14 completion. External mode requires an actual observed external value, an unchanged whole-values hash across stages, and the separate operator confirmation. Flux ownership remains unchanged.

The next concrete CNPG implementation must use a separate backend binding, retaining the existing single-Pod/PVC observer unchanged. The binding must capture namespace UID, original Helm revision UID, observed backend values hash, chart-selected Cluster name, Cluster UID/generation, application database/user, read-write Service UID and application Secret UID/resourceVersion. The exact chart derives the Cluster name through astronomer.cnpgClusterName and uses the Cluster-generated <cluster>-app Secret uri; enableSuperuserAccess=false supplies no legacy POSTGRES_USER/POSTGRES_DB environment. No authority can come from label absence or an operator schema assertion.

1. Add CNPGDatabaseObservation with fresh postgresql.cnpg.io Cluster Ready condition, currentPrimary, instance count, and observed generation. Select only a Pod owned by the captured Cluster UID, with cnpg.io/cluster and primary role consistent with that currentPrimary. Bind each data PVC/PV claimRef and Pod volume reference, and verify the RW Service's ready Endpoints/EndpointSlice target Pod UID. App Secret data stays private; bind the Secret metadata/content identity without putting credentials in logs/public report or process argv.
2. Implement source schema observation and logical custom-format backup through the bound primary's actual local PostgreSQL command contract. Confirm the real image's supported local peer-auth command before qualification; do not invent legacy environment variables. Require actual major and clean compatible schema, immutable source Cluster/namespace identity and primary binding before/after each dump. A primary handoff during a dump yields a retained partial/unknown failure and no complete backup publication. Between stages, a newly Ready primary may be admitted only if it still belongs to the same Cluster UID, exact PVC/Service/Secret ownership and unchanged original database/schema. Never relax the captured legacy Pod UID rule for the bundled adapter.
3. Restore the retained custom-format dump into an exclusively owned disposable database workload/cluster using the same qualified PostgreSQL major and exact selected image. Capture creation UID and private recovery marker before acknowledging it. Validate actual pg_restore list/restore, clean schema and encrypted-row proof there. Cleanup must use current UID/role/OID/marker admission; never CREATE/DROP/restore into an unknown application database or source CNPG cluster. Preserve partial backup/restore/checkpoint material on cancellation or unknown outcome.
4. Add CNPG target observation to the shared Driver backend interface. Freshly qualify target Cluster UID, health/primary/service/secret and actual application schema before readiness/reporting. Helm update cannot automatically change PostgreSQL major, mutate upstream CNPG operator/Flux ownership or discard the Barman Cloud plugin/ObjectStore configuration. A same-name recreated Cluster cannot inherit old callbacks or a backup lease. Rollback needs actual schema reversibility and owned current release/database observations.
5. Add genuine fixtures for old primary held during failover, same-name recreated Cluster/Secret/PVC, failed dump/restore/cancel and owner-preserving retry. Then run the real owned PG17/18 and CNPG multi-instance rehearsal serially under fresh namespace/Cluster/primary/Service/Endpoints/PVC/major/schema fences. Those runtime gates are required before claiming CNPG upgrade compatibility, PITR/Barman restore, successful whole Driver or W14 completion.

No CNPG/PG/kubectl/native operation was executed while authoring this proposal. This explicit refusal removes the false weaker assurance path immediately; the concrete adapter remains an implementation task in the complete W14 scope, not a permanent deferral.
