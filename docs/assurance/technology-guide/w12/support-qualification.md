## CNPG recovery and observed bounds

The owned CNPG18 fixture used three instances and one synchronous standby on K3s1.36.5. A persistent production pgx pool wrote a synthetic monotonic/idempotent ledger while the current owned primary pod was deleted. One sample observed62 acknowledged writes,22 transient write failures, zero acknowledged rows lost, a21.524s maximum successful-write gap and23.520s from fault to the new primary's committed write. Cluster and all three PVC UIDs remained unchanged and all instances recovered. These are measurements of this workload and fault, not a whole-application or monthly-availability guarantee.

The physical backup was restored to a new owned cluster with new PVCs. All202 public/marker table counts matched. Production readers recovered old legacy and current encrypted credentials, key IDs, Charlie TLS identity, agent token/tenant bindings, delivery generations and scoped audit intent details. The independently copied protected key reference was required; missing old and wrong keys failed. Audit intent/outbox recovery is qualified; a native cryptographic audit chain is not implemented or claimed. No PITR claim is made.

The first restore failed because the online backup's required final WAL had not been archived, despite the Backup resource reporting completion. The source archiver had reached segment15 while the backup required16. An explicitly owned WAL switch and archive completion preceded the successful retry. Before a recovery receipt can pass:

1. Bind the Backup, source Cluster and ObjectStore identities, exact backup ID, immutable image and required end-WAL to the owned namespace.
2. Verify the required end-WAL is present in the intended object-store prefix. A `Completed` Backup status alone is insufficient.
3. Restore into a fresh Cluster/PVC set without enabling archival to the source prefix; bound endpoint readiness before invoking production readers.
4. Compare table/count and application invariants, retrieve keys independently, and run missing/wrong-key negatives.
5. Retain each failure and the explicit remediation. The root receipt discloses that the initial Service-readiness CLI log was overwritten; only the session output survived. The end-WAL failure log was retained.

Standalone PostgreSQL streaming/SIGKILL/pg_ctl promotion remains a separate lane. It does not prove CNPG operator ownership, Barman plugin behavior, service reconciliation or a fresh operator restore. Neither a script's zero exit nor configured30s/zero-row thresholds establish a universal RTO/RPO.

## Browser, Kubernetes and accessibility limits

Chromium components on the frozen combined source passed21 cases, and the full frontend passed340 files/2364 tests. Cross-engine component and live receipts must name exact Playwright/browser builds, projects, widths, one-worker settings and zero retries. Components exercise real rendering with scoped HTTP fixtures. Live auth, refresh rotation, revocation, mutation validation, recovery, upload/download, streams and cancellation require actual owned-server receipts.

WebKit exposed a ResizeObserver feedback cycle when synchronous external-store publication triggered React layout changes in the observer cycle. The bounded virtualizer correction defers measurement publication to the next animation frame. [TanStack documents](https://tanstack.com/virtual/latest/docs/api/virtualizer#useanimationframewithresizeobserver) an approximately16ms delay and possible stale measurements/visual artifacts; it discourages general use. This is a measured correction for this specific cycle, not a performance optimization. Browser regression checks retain strict page-error assertions, variable row measurements, far-window focus recovery, selection, sorting, grouping and filtering. The pending-dialog fixture holds its response until Cancel completes, avoiding a fixed-delay race without canceling the durable save.

Scoped axe WCAG2A/2AA/2.1AA checks and semantic/keyboard tests are automated coverage. Shipping Safari and human accessibility remain separate: qualify the release's actual current/previous Safari versions on named macOS and iOS releases, with real-device keyboard/VoiceOver and assistive-technology sessions. Playwright WebKit is not that certification. Dated primary targets observed2026-10-09 are Safari 27.0 (Apple release-note build20625.1.29) on macOS Golden Gate27.0.1/Tahoe26.7.1/Sequoia15.8.1 and iOS/iPadOS27.0.1, plus previous Safari26.6.1 on macOS Sonoma14.8.9. Apple lists [Safari27](https://support.apple.com/en-us/149039) as final on2026-09-14 and [Safari26.6.1](https://support.apple.com/en-us/148286) on2026-08-18; its [release table](https://support.apple.com/en-us/100100) supplies the OS patches. Previous mobile OS26.7.1 is a separate integrated-browser lane whose actual UA/WebKit build must be captured. The [primary target record](safari-primary-targets.json) retains byte hashes, dates and platform distinctions. Recheck before execution; none of these real-device campaigns has run, and an OS patch number is not a claimed Safari app version.

[CNPG1.30](https://cloudnative-pg.io/docs/1.30/supported_releases/) supports Kubernetes1.34/1.35/1.36 and lists1.37 as tested but not supported. Its upstream distribution support is vanilla Kubernetes; owned K3s qualification does not invent another vendor certification. Keep1.36 as the production vendor-supported transition lane and1.37 experimental. The [Kubernetes skew policy](https://kubernetes.io/releases/version-skew-policy/) requires kubectl within one minor of the API server. The host's1.34 client cannot qualify1.36; an independently checksum-verified1.37 client is used for owned1.36/1.37 lanes. Preserve the historical published1.33–1.35 range as unknown for a new candidate until actual candidate receipts exist. Verify client-go, Flux and Helm interfaces as part of the candidate, rather than equating a healthy operator pod with a healthy whole application.
