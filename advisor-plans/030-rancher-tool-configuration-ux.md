# Plan 030 — Exceed Rancher's supported-chart configuration UX

## Status and scope

**IN PROGRESS — install authoring and the first upgrade/preflight increment are implemented in the qualification branch.** This plan covers the configuration, review, lifecycle feedback and destructive-action UI for Astronomer's twelve Tool entrypoints and all 21 supported catalog applications. It complements Plan 028's API qualification: an installation is not usable merely because the API accepts it, and a polished form does not qualify the underlying chart.

The reference is the checked-out Rancher Dashboard and Rancher chart source in this workspace. The goal is to retain Rancher's proven interaction patterns while making effective values, multi-release ownership and recovery more explicit.

## Deep Rancher comparison

The comparison is against behavior in the local source, not screenshots or memory. Rancher's generic engine in `shell/components/Questions/` supports string, multiline, password, hostname, IP, CIDR, cron, boolean, enum, integer, float, array, map, YAML, radio and live resource references including Secret, ConfigMap, StorageClass and PVC. It also supports groups, nested subquestions, conditional visibility, descriptions, tooltips, character rules, length/range checks and translated labels. Its chart install page adds version selection, chart README, Form/YAML/Diff modes, existing-value hydration, preservation of customized values across version changes, auto-installed dependencies and advanced Helm execution controls. Its monitoring, Gatekeeper, Istio and backup forms add product-specific logic that a generic questions file cannot express cleanly.

## Interaction contract

1. **Settings** shows a short, curated set of high-value values grouped by operator intent: scaling, storage, resources, networking, monitoring, scheduling and general behavior. Display the effective preset value without serializing it as a user override.
2. **YAML** accepts all advanced values. Switching back to Settings preserves unknown keys and projects known values into the form. Invalid or non-object YAML blocks Review and Install with an inline error.
3. **Review** calls the same public preview API used by automation with the selected preset and current override. Every managed monitoring-stack install passes through this review. Tools show the ordered release plan and server-merged diffs. Apps show immutable chart identity, digest, namespace and checks; an App default-to-effective diff remains an explicit follow-up rather than a client-generated approximation.
4. **Install** sends only explicit operator overrides. The server validates curated field types and enumerations even for direct API callers, deep-merges distribution defaults, preset and overrides, then persists one durable ordered plan.
5. **Progress and recovery** show each release independently, preserve failure detail, and offer only actions the backend can complete. A preview, accepted request or Ready pod is never presented as successful functional validation.
6. **Uninstall** requires the tool name, explains chart-owned versus retained resources, and records progress in the same operation surface. Tools with an upstream deletion guard require an explicit API field and product-owned preparation step; the UI must not tell users that retained storage is certainly deleted or preserved.

For supported charts with `values.schema.json`, ingestion merges those definitions over a complete type schema inferred from the pinned `values.yaml`, preserving upstream descriptions, enums and bounds without losing paths omitted by a partial schema. `questions.yaml`/`questions.yml` adds Rancher-compatible labels, descriptions/tooltips, required fields, defaults, groups, types, enums, ranges, length limits, reference-kind metadata and simple conditions. Version-aware Astronomer overlays project the high-value paths listed above for all 21 supported applications. Most paths must exist in the selected chart; a small audited set of optional template/subchart values, such as Grafana persistence and Loki bucket names, carries an explicit fallback schema because upstream defaults omit it. Unsupported charts retain the complete generated form. YAML remains the complete surface and form edits preserve every uncurated key. Schema presence never changes support tier, compatibility or qualification status.

The pinned chart audit also treats renderability as part of authoring. The Loki chart requires bucket names for object storage, and the OpenTelemetry Collector chart requires both a deployment mode and image repository; both are promoted and enforced before mutation. Resource request/limit controls receive an audited Kubernetes resource schema when charts declare only an empty object. Kube Prometheus Stack now promotes the same core choices Rancher exposes—scrape and rule intervals, retention, replicas/shards, admin and namespace-selector policy, Prometheus and Alertmanager PVC settings, existing Alertmanager/Grafana Secrets, Grafana persistence and component enablement—while keeping every advanced upstream value in YAML.

## Verification

- Unit tests must prove YAML → Settings → YAML retains uncurated nested values, form edits emit only explicit overrides, invalid YAML cannot install, and Review sends the override to the preview endpoint.
- Handler tests must prove direct API requests receive the same curated type/enum validation as the UI and multi-release values are partitioned by `values_key`.
- Live browser validation must exercise all three modes with at least one single-release and one multi-release Tool.
- Plan 028 remains the authority for install, canary, RBAC, upgrade, rollback, restart recovery, uninstall and cleanup PASS/FAIL evidence.
