## 1. Objective

Build and run one reproducible qualification campaign proving that:

1. Astronomer and Constellation can run together on an operator-owned three-node
   management cluster.
2. Three additional operator-owned servers can be repeatedly converted into:
   - a single-node K3s cluster;
   - a single-node RKE2 cluster;
   - a three-server high-availability K3s cluster using embedded etcd;
   - a three-server high-availability RKE2 cluster using embedded etcd.
3. Every resulting cluster can be adopted through Astronomer's documented API,
   connect using the generated outbound agent, receive the exact Flux distribution,
   and converge managed workloads.
4. Astronomer can discover pre-existing workloads and perform supported workload
   lifecycle operations through its API without falsely claiming ownership of
   resources it did not create.
5. Constellation can register the same cluster, reach healthy controller/sensor
   state, report the deliberately selected image vulnerabilities, and observe the
   expected east-west, north-south, DNS, denied, and recovery traffic generated by
   the workload suite.
6. Repeated clean installs produce the same result, with failures, timing,
   provenance, independent observations, and cleanup recorded in a closed evidence
   bundle.

This is qualification of already-provisioned clusters. It does not add cluster
provisioning to Astronomer and must not present K3s/RKE2 installation as an
Astronomer product feature.

## 4. Physical and logical architecture

The minimum lab has six distinct servers or VMs:

```text
management-1 ─┐
management-2 ─┼─ three-node management Kubernetes cluster
management-3 ─┘    ├─ Astronomer server/worker/frontend + dependencies
                    └─ Constellation management/controller components

target-1 ─┐
target-2 ─┼─ repeatedly wiped and rebuilt as one qualification topology
target-3 ─┘    ├─ K3s or RKE2
                ├─ Astronomer outbound agent + release-pinned Flux
                ├─ Constellation sensor/enforcer components
                └─ qualification workload suite

orchestrator host
  ├─ exact Astronomer and Constellation source clones
  ├─ SSH access only to target-1..3
  ├─ read-only management kubeconfig except explicit product installation
  ├─ API tokens for both products, supplied through environment variables
  └─ evidence directory outside both repositories
```

The management nodes and target nodes must never overlap. The harness must compare
machine IDs, addresses, SSH host keys, and management-cluster node identities and
abort on any intersection.

### 4.1 Network requirements

- All nodes have synchronized time and stable forward/reverse identity.
- Target nodes can resolve and reach the Astronomer and Constellation endpoints,
  OCI/image registries, and any approved package/chart sources.
- The Astronomer agent requires outbound connectivity only; the harness must not
  open inbound management access to the target Kubernetes API merely for product
  convenience.
- The orchestrator may reach the target API endpoint for independent verification.
- Three-node K3s and RKE2 use a stable registration address represented by a
  pre-provisioned load balancer or an explicitly approved VIP. The chosen mechanism
  and failover behavior are part of evidence.
- Required K3s/RKE2 and etcd peer ports are open only between the three target hosts.
- Constellation-required ports and kernel features come from the pinned
  Constellation contract, not assumptions in this plan.
- DNS, HTTP, HTTPS, TCP, UDP, allowed east-west, denied east-west, and controlled
  egress paths used by the workload suite are declared before execution.

## 6. Destructive safety model

The harness must implement all of these before it gains an `execute` mode:

- [ ] Default mode is `plan`; `execute` requires `--inventory`, `--campaign-id`,
  and the exact `--destructive-ack` string.
- [ ] Resolve each SSH host to one canonical address and compare it to the signed
  inventory before any privileged command.
- [ ] Pin SSH host keys; never use `StrictHostKeyChecking=no`.
- [ ] Read `/etc/machine-id`, hash it locally, and compare with the inventory.
- [ ] Collect management-cluster node machine IDs and addresses and prove the
  target set is disjoint.
- [ ] Require a host ownership marker whose campaign ID, owner, and expiry match
  the inventory.
- [ ] Reject symlinked inventory, kubeconfig, SSH key, registry auth, evidence,
  and driver paths.
- [ ] Reject world-readable secret inputs and evidence roots.
- [ ] Reject an empty, root, home, workspace-root, or unresolved cleanup path.
- [ ] Never interpolate unvalidated inventory data into a shell command. Pass
  values as positional arguments or closed environment variables.
- [ ] Use exact service and path allowlists for cleanup; no broad `rm -rf` target,
  wildcard service stop, or ambient process kill is permitted.
- [ ] Tag every created Kubernetes object and remote file with campaign/run IDs.
- [ ] Register cleanup traps before the first remote mutation.
- [ ] Write a failure evidence manifest even when preflight or bootstrap fails.
- [ ] A failed cleanup is a failed run and blocks reuse of that host.
- [ ] After two failed cleanup attempts, STOP and require operator reimaging.
- [ ] Never delete an Astronomer or Constellation cluster record unless its
  external ID, run label, target machine IDs, and campaign ID all match.

Negative harness tests must prove that a wrong acknowledgement, wrong host key,
wrong machine ID, management/target overlap, expired ownership, symlinked input,
unexpected existing Kubernetes installation, unexpected workload, or extra target
causes zero remote mutation.

## 7. Required topology and repetition matrix

The release-blocking matrix contains twelve runs:

| ID | Distribution | Topology | Hosts | Repetitions | Role shape |
|---|---|---|---|---:|---|
| K3S-SINGLE | K3s | single node | rotate target-1, target-2, target-3 | 3 | one schedulable server |
| RKE2-SINGLE | RKE2 | single node | rotate target-1, target-2, target-3 | 3 | one schedulable server |
| K3S-HA3 | K3s | three-node HA | target-1..3 | 3 | three schedulable server/etcd nodes |
| RKE2-HA3 | RKE2 | three-node HA | target-1..3 | 3 | three schedulable server/etcd nodes |

Two non-blocking characterization runs should follow if capacity permits:

| ID | Distribution | Topology | Purpose |
|---|---|---|---|
| K3S-1S2A | K3s | one server, two agents | Distinguish role topology from control-plane HA |
| RKE2-1S2A | RKE2 | one server, two agents | Distinguish role topology from control-plane HA |

qualify management continuity after one server failure.

systematically favor one product. A valid example is:

1. K3S-SINGLE r1 on target-1
2. RKE2-SINGLE r1 on target-2
3. RKE2-HA3 r1
4. K3S-HA3 r1

Every run begins after cleanup validation and a reboot, and ends with evidence,

| Flux controllers and baseline | 15 minutes |
| Managed workload rollout | 10 minutes |
| Constellation full sensor health | 10 minutes after installation |
| Known vulnerability observation | 20 minutes after workload Ready |
| Network-flow observation | 3 minutes after correlated traffic completes |

## 11. Evidence contract

Implement `qualification/three-host/evidence.schema.json` with a closed schema.
Every run writes `evidence.json` atomically on success or failure. The campaign
aggregator accepts exactly the twelve required successful run identities, rejects
duplicates/missing runs/mixed commits/mixed release digests, and emits
`campaign-evidence.json`.

Required provenance:

- campaign ID, run ID, attempt, topology ID, repetition, phase, status;
- started/completed timestamps and monotonic phase durations;
- Astronomer repository/ref/commit/tag, release manifest digest, chart digest,
  image digests, Flux distribution and bundle digests;
- Constellation repository/ref/commit/tag, release/chart/image/sensor digests, and
  API contract version;
- orchestrator source-tree hash and tool versions;
- target host IDs, hashed machine IDs, host-key fingerprints, OS/kernel/runtime
  facts, registration endpoint mode, and node role map;
- management cluster UID and node identity hashes without kubeconfig contents;
- Astronomer, Kubernetes, and Constellation cluster IDs;
- exact thresholds and result for every required check;
- sanitized failure category and failed phase;
- artifact path, size, media type, and SHA-256 for every retained file;
- cleanup start/end, exact owned resources removed, residual checks, and result.

Required artifact layout:

```text
<campaign-id>/
  inventory.redacted.json
  thresholds.json
  source-tree.json
  campaign-events.jsonl
  runs/
    <run-id>/
      evidence.json
      evidence.sigstore.json
      host-facts/
      bootstrap/
      kubernetes/
      astronomer/
      constellation/
      workloads/
      traffic/
      faults/
      cleanup/
      screenshots/
  campaign-evidence.json
  campaign-evidence.sigstore.json
```

Sanitization requirements:

- Never retain kubeconfigs, bearer tokens, bootstrap passwords, registry auth,
  SSH keys, Secrets, full environment dumps, raw Authorization headers, session
  cookies, or Constellation auth state.
- Kubernetes YAML collection must exclude Secret data and redact known sensitive
  annotations.
- Logs pass through the repository redaction patterns plus Constellation's own
  redaction contract.
- Evidence validation rejects symlinks, extra unmanifested files, credentials,
  missing hashes, absolute host paths, or world-readable files.
- Preserve raw product API responses only after schema-aware sanitization.
- Sign each run and the aggregate with the approved CI/workflow identity; verify
  signature identity, source commit, source ref, workflow, run ID, and freshness.

## 16. STOP conditions

Stop immediately and report if:

- Constellation source/contracts are unavailable or a required capability cannot
  be mapped to a real API/CLI and independently verified.
- Management and target host sets overlap by address, machine ID, SSH host key, or
  Kubernetes node identity.
- The target ownership/expiry/acknowledgement does not match exactly.
- A target contains unknown workloads, retained data, an unapproved Kubernetes
  installation, or an unrecognized storage/network agent.
- Any host requires disabling SSH verification or exposing a secret to proceed.
- K3s/RKE2 version, checksum, signature, architecture, kernel, CNI, or runtime is
  outside either product's supported matrix.
- The HA registration endpoint is not stable before installation.
- Astronomer or Constellation release provenance cannot be verified.
- A run would require editing product code or relaxing a threshold after results
  are observed.
- A mandatory check is unsupported or skipped.
- Evidence contains a credential or cannot be sanitized without destroying the
  claim being proven.
- Cleanup is incomplete after two attempts or a host cannot reboot cleanly.
- The same unexplained failure occurs twice; stop repeating and diagnose it.
